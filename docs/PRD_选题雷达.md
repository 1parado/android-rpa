## 1. 背景与问题

内容创作者最大的持续痛点是「下一个视频做什么」：

- 热榜/排行每天变化，人工刷新无规律、留不下记录；
- 现有第三方工具（新榜等）提供的是**平台级**热点数据，拿不到「算法推给你的内容」；
- App 首页推荐流是平台对账号标签的实时反馈，**只存在于手机 App 内**，PC 网页的推荐与之不同——这是本产品唯一的数据壁垒。

本项目已有成熟的手机 RPA 底座（uiautomator2 + 人味风控 + dry-run + 人为打断），新增一个 B 站采集模块的边际成本很低。

## 2. 目标用户与场景

| 用户 | 场景 | 频率 |
|---|---|---|
| 个人创作者（B站/未来快手） | 每天早上看一份「今日热点 + 推荐流升温分析」报告，决定当天拍什么 | 每日 1 次 |
| 内容团队运营 | 每周汇总选题趋势，安排一周排期 | 每周 1 次 |

前提：用户拥有自己的 B 站账号（登录态在手机 App 内），手机通过 USB/无线 adb 连接常开的 PC。

## 3. 产品目标与成功指标

- **北极星指标**：用户基于报告产出的视频数（人工统计）。
- **过程指标**：
  - 采集成功率 ≥ 95%（单日任务失败自动重试 + 告警）；
  - 推荐流去重后日均采集 ≥ 40 条有效视频卡片；
  - 报告生成耗时 ≤ 5 分钟（含 LLM 分析）。
- **零红线**：全程只读，不点击视频、不点赞投币、不关注，无账号风险。

## 4. 需求范围

### 4.1 MVP（本期）：B 站选题雷达

三个数据源 + 一份日报：

| 模块 | 说明 | 优先级 | 验收口径 |
|---|---|---|---|
| F1 热榜采集 | B 站热搜榜标题 + 热度值 | P0 | MVP 必须出数 |
| F2 推荐流采集 | App 首页推荐流滑动 N 屏，采集视频卡片（标题/UP主/播放量），跨日去重 | P0 | MVP 必须出数 |
| F3 分区排行采集 | 指定分区排行榜前 N 标题 + 数据 | P1 | 入口命中才出数，找不到可整日缺省 |
| F4 LLM 日报 | 汇总近 3 天数据，输出「升温话题 + 选题建议」Markdown 日报 | P0 | 有 LLM key 必须产出；无 key 降级为仅落盘并 log 提示 |
| F5 数据留存 | CSV/JSONL 按日落盘，积累个人数据仓库 | P0 | MVP 必须落盘 |

### 4.2 路线图（后续版本，本期不做）

- **V2 竞品追踪**：定时遍历对标账号主页，采集新视频数据，识别「异常爆款」即时推送；与推荐流共用「采集-去重-LLM-推送」引擎。
- **V3 评论舆情 + 数据日报**：自己视频的评论区/弹幕情绪分析周报；创作中心 App 端数据每日截图采集，攒成历史曲线。
- **V4 多端分发流水线**：一次创作自动分发 B站/快手/抖音（首个含写操作的版本，需独立风控评审）。

## 5. MVP 功能需求详述

### F1 热榜采集

- 路径：启动 App → 首页搜索框（`text~="搜索"` 或 `desc` 含「搜索」）→ 进入搜索页 → 「B站热搜」区域 → 逐屏读取榜单条目文本。
- 采集字段：`rank, title, heat, collected_at`；写 `hot_search_YYYYMMDD.csv`。
- 热度值允许缺失（部分条目不展示数值），缺失置空不阻塞。
- 兜底：若热搜入口找不到，记录异常截图并跳过该数据源（不阻塞 F2）。

### F2 推荐流采集（核心差异化）

- 路径：冷启动 App → 首页「推荐」tab → **先 human_delay 预热 60-90s（模拟真人停留，关闭开放问题①：采纳预热）** → 循环 `swipe_direction("up")` 共 N 屏（默认 8，可配置）→ 每屏读取可见视频卡片文本节点。
- 采集字段：`title, uploader, play_count, collected_at`；同一会话内按 title 去重。
- 卡片解析规则（dump 文本节点 → 结构化）：
  - `title`：长度 ≥ 6 的长文本节点，排除 UI 标签白名单（推荐/热门/直播/分区名/导航词）；
  - `uploader`：`title` 节点下方 200px 内、以「UP主名 · xxx播放」格式或独立短文本节点匹配；
  - `play_count`：从「xx万播放 / xx观看」模式文本正则提取，允许缺失；
  - MVP 接受少量噪声（解析失败的行丢弃并计数），由 LLM 侧容错。
- 跨日去重：复用 `core/state.py` 的「增量写 + TTL」模式（不新造轮子），库存 `data/bili_radar/seen_titles.json`，记录标题 hash → 最近采集时间，TTL 7 天。采集到已见标题时更新时间戳并在记录中带 `first_seen/seen_count`，供 F4 的「升温」对比。

### F3 分区排行采集（P1）

- 路径：首页「热门」tab → 排行榜入口 → 按分类采集（默认：科技、知识；关闭开放问题②）。
- 采集字段：`region, rank, title, play_count, collected_at`。
- 入口找不到时降级跳过（当日 ranking CSV 缺省不算失败）。

### F4 LLM 日报

- 输入：当日三源 CSV + 近 3 天历史（seen 库对比增量）。
- Prompt 要求输出：
  1. 热榜与推荐流的交叉话题（两边都出现的题材 = 强信号）；
  2. 推荐流中「升温」的内容类型（同题材标题 3 天内频次上升）；
  3. 3-5 条具体选题建议（含参考标题结构与切入角度）。
- LLM 配置：**新增 `config.LLM`**（v0.1 误写为「沿用现有配置」，实际不存在），OpenAI 兼容 chat/completions：
  ```python
  LLM = {
      "base_url": os.environ.get("ANDROID_RPA_LLM_BASE", "https://api.deepseek.com/v1"),
      "api_key": os.environ.get("ANDROID_RPA_LLM_KEY", ""),
      "model": os.environ.get("ANDROID_RPA_LLM_MODEL", "deepseek-chat"),
  }
  ```
- 降级：`api_key` 为空 → 跳过日报生成，log.warning 提示配置方法，采集数据照常落盘。

### F5 数据留存与报告输出

```
data/bili_radar/
├── hot_search_YYYYMMDD.csv
├── feed_YYYYMMDD.csv
├── ranking_YYYYMMDD.csv          # P1，缺省日无文件
├── seen_titles.json              # 去重库（TTL 7 天，复用 state 模式）
└── reports/
    └── topic_radar_YYYYMMDD.md   # LLM 日报（无 key 时不生成）
```

CSV 统一 UTF-8（带 BOM，Excel 直开不乱码）；JSONL 不使用，统一 CSV。

## 6. 技术方案（映射现有架构）

| 现有能力 | 在本需求中的使用 |
|---|---|
| `apps/boss_zhipin.py` 模块模式 | 新增 `apps/bilibili.py`，`run(r, ...)` 为唯一入口 |
| `Robot.find(text/text_contains/desc)` | 交互入口（搜索框/tab）按可见文本定位，不依赖 resource-id |
| `Robot.swipe_direction(scale)` | 推荐流翻屏 |
| dump_hierarchy 文本节点批量读取 | **模块内实现 `_dump_texts(r)`**（v0.1 误写为 `Robot.phone_ui_texts`，该方法不存在）；同时把 boss_zhipin 的 `_nodes_with_bounds` 抽到 `core/actions.py` 作为 `Robot.dump_texts()` 公共方法，两处复用 |
| `config.RATE` 风控 | 滑动间隔随机 3-8s（human_delay 自带）；采集任务 `op_budget` ≤ 60 |
| dry-run 优先 / 人为打断 / 异常截图 | 原样继承，不新增机制 |
| `core/state.py` 增量写 + TTL | seen 去重库参照该模式实现（BILI 版 schema 不同，单独文件） |

### 接线改动清单（全部一次 PR 完成）

1. `config.py`：`PACKAGES["bili"] = "tv.danmaku.bili"`；新增 `BILI = {...}`、`LLM = {...}`
2. `core/actions.py`：新增 `Robot.dump_texts()`（返回 `[(text, bounds_dict), ...]`）
3. `apps/bilibili.py`：采集 + 落盘 + 日报主逻辑
4. `main.py`：`--task` 增加 `bili`；`--screens` 参数透传推荐流屏数

### 跨机型通用性设计（硬性要求）

1. **只用文本/描述定位**，不用 resource-id（各机型/版本差异大）；
2. 坐标类操作一律按 `d.window_size()` 屏幕比例计算；
3. 查找失败多级兜底：精确文本 → 包含文本 → 区域内文本扫描（按 y 坐标范围过滤节点），全部失败则截图留痕并跳过；
4. 对 App 改版的适应策略：模块内所有选择器集中定义在文件头部 `SELECTORS` 字典。

## 7. 非功能需求

- **只读红线**：模块内禁止点击视频卡片/点赞/关注类操作；tap 白名单仅限「搜索框、tab 切换、弹窗关闭按钮」；进入非预期页面立即 `press_back()` 返回。
- **频率**：每日 1 次，建议时段 08:00-10:00；单次会话上限 60 ops，超限自停。
- **失败处理**：任一数据源失败不影响其余数据源；全失败时告警（log.error + 退出码非 0，微信通知留 V2）。
- **隐私**：采集数据仅存本地，不上传第三方；LLM 分析会把标题文本发给所配 LLM 服务商（DeepSeek），在 README 中注明。

## 8. 验收标准

- [ ] 连续 3 天定时运行，P0 源（热榜/推荐流）CSV 均有数据，成功率 ≥ 95%（F3 命中出数即可，缺省不算失败）
- [ ] 两台不同分辨率/品牌的设备上 dry-run 与 live 均通过（跨机型验证；单设备阶段先过本项的自测子集）
- [ ] 同一视频跨日重复出现时，seen 库正确更新 `seen_count`，日报的「升温」判定能引用历史频次
- [ ] 中途 `stop_agent.bat` 打断后重跑，seen 库不重复采集
- [ ] 有 LLM key 时日报包含：交叉话题、升温类型、≥3 条选题建议；无 key 时采集照常落盘并有明确 log
- [ ] 全程无任何写操作日志（tap 视频卡片/点赞类）

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| B 站改版导致入口/文案变化 | 单源采集失败 | 选择器集中管理 + 失败跳过不阻塞 + 截图留痕快速修 |
| 冷启动有开屏广告/弹窗 | 流程阻塞 | 采集前统一的「弹窗清理」步骤（跳过/关闭/我知道了/稍后再说/取消 文本白名单） |
| 推荐流卡片控件非标准列表 | 文本节点混杂 | 按解析规则过滤，MVP 接受少量噪声，LLM 侧容错 |
| 未登录/风控验证页 | 任务失败 | 检测到「登录/验证」引导文本时告警终止，提示人工登录 |
| dump_hierarchy 偶发超时/空树 | 单屏采集失败 | 重试 2 次，仍失败按本屏无数据继续 |
